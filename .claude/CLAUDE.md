# CHIDAOBA website: project notes

Static site generated by `_src/build.py` (English + Georgian), hosted on GitHub Pages, Supabase backend.
Build: `python3 _src/build.py`. Bump `ASSET_V` whenever CSS or JS changes. Georgian strings live in `_src/i18n/ka.json`.

## Design work
For any design, redesign or polish task, load the **design-taste-frontend** skill (`.claude/skills/design-taste-frontend/`, from
github.com/Leonxlnx/taste-skill, MIT) and follow its run: brief, direction, build, inspect, look at screenshots, fix.

The owner's decisions below override the skill's house rules where they conflict:
- Brand name is **CHIDAOBA** only (never "CHIDAOBA CULTURE"). Colours: carbon #1E1E1E, chalk #F2F1EC, red #B5212F.
- Rounded corners were requested ("soft, like Apple products"). Keep them unless the owner agrees to change.
- Section numbering such as "01 · ჩემპიონები" is part of the owner's own copy; keep it unless the owner agrees to drop it.
- Georgian pages use the Gremi Web font (`assets/fonts/gremi-web.woff`) for all Georgian letters, digits and basic punctuation.
- Copy: plain and professional, no slogans, no long dashes (—), no source lists, don't repeat the same fact.
- Shop: Men / Women / Kids kept separate, WhatsApp ordering only. Camps: no deposits.
- Do not use the Mulakhi venue photos on Why Georgia. Community and Journal stay hidden.
When a skill rule would change one of these, propose it to the owner with a before/after instead of applying it.

## Before saying "done"
Check every touched page at 1400px and 390px, in English and Georgian: screenshots looked at, no sideways scrolling,
no JS errors, no untranslated English on Georgian pages. Confirm the GitHub Pages deploy finished.

## Security
Only the Supabase anon key goes on the site. Never ask for the service_role key, database password or third-party API keys.
Database changes ship as numbered files in `_src/migrations/` (`012_short_name.sql`, next number up), safe to run twice,
tested locally first. Pushing to main applies them automatically (`.github/workflows/supabase-updates.yml` runs
`_src/migrate.py`, which records each one in `public._migrations`). The owner never pastes SQL by hand; check the
Actions run succeeded; its log ends with a "Database health" report (structure and counts, no personal data) that shows the live database. The token lives only in the GitHub secret SUPABASE_ACCESS_TOKEN; never ask for it.
